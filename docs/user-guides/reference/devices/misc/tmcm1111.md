# TMCM-1111 fraction collector

Flowchem supports the Analog Devices / TRINAMIC TMCM-1111 StepRocker as a single-axis linear fraction collector over
the USB virtual serial port.

Positions are configured in raw TMCM microsteps. Calibrate these values on the real rail and use names such as
`waste`, `vial_1`, or `vial_2` in experiment scripts.

## Configuration

```toml
[device.fraction_collector]
type = "TMCM1111"
port = "COM7"
positions = { waste = 0, vial_1 = 12000, vial_2 = 24000 }
home_position = "waste"
home_on_initialize = false
```

`home_position` is optional. The reference search always zeros `ACTUAL_POSITION` at the calibrated switch location
regardless of this setting (that's a property of the motion controller's own reference-search state machine, not
something Flowchem controls) — so if the position at your switch is already named `0` in `positions` (as in the
example above), you can leave `home_position` unset entirely; `get_position()` will still resolve it to that name.
Set `home_position` only if you want the switch location to map to something other than `0` in your numbering.

The serial connection follows the same pattern as other Flowchem serial devices. `port` is required; the following
serial settings are optional and default to the TMCM-1111 USB serial defaults:

```toml
baudrate = 9600
timeout = 1
bytesize = 8
parity = "N"
stopbits = 1
```

Reference-search and motion settings all have working defaults already (see below) — override them explicitly only
if your rail/motor needs different values:

```toml
reference_search_mode = 1
reference_search_speed = 51200
reference_switch_speed = 4096
reverse_shaft = true
max_positioning_speed = 51200
max_acceleration = 500000
```

### Where these defaults come from

`TMCM1111.from_config` ships concrete defaults for `reference_search_mode` (`1`), `reference_search_speed`
(`51200`), `reference_switch_speed` (`4096`), `reverse_shaft` (`true`), `max_positioning_speed` (`51200`), and
`max_acceleration` (`500000`) — you don't have to set any of them to get a working `home()`/`PUT /position`. These
are **not** universal constants: they're the working configuration for one specific board and rail calibrated
against real hardware in this project (mode 1 + `reverse_shaft = true` gives a clean, switch-triggered home on that
unit; the speeds are safe magnitudes for its motor). `reverse_shaft` in particular is a per-physical-board
rotation-direction quirk, not a per-model one — two TMCM-1111 units can need opposite values for the same
`reference_search_mode`. Treat every one of these as a documented starting point to verify against your own
hardware, not as guaranteed-safe for any TMCM-1111. (The underlying shared driver class still defaults each of
these to "leave this axis parameter untouched" — `TMCM1111` is what layers the concrete values on top.)

### Homing the wrong physical side

`reference_search_mode` picks which switch/direction is searched (see the TMCL firmware manual's reference-search
modes, e.g. mode 1 searches the left stop switch only), but which real-world rotation direction a board treats as
"left" vs "right" is not guaranteed to be the same across individual 1111 units — two boards can rotate opposite
ways for the *same* `reference_search_mode` value. `reverse_shaft` defaults to `true` here because that's what the
board this driver was validated against needed; if homing consistently ends up on the wrong physical side on
*your* unit (or worse, keeps driving into the mechanical end stop instead of stopping cleanly on a switch), try:

```toml
reverse_shaft = false
```

This maps to axis parameter #251 ("Reverse shaft"), applied at every `initialize()` since it's volatile
(SRAM-only, reset on power-cycle). It only flips rotation direction — it does not change which switch a given
`reference_search_mode` value targets — so whichever value is correct for your board, the same
`reference_search_mode` should still produce a clean, switch-triggered stop. The device log reports the board's
current value of this parameter on every `initialize()`, so you can check what's actually on the device.

### `PUT /position` not moving the motor

`PUT /position` uses the `MVP` command, which rules its own ramp via axis parameters #4 (maximum positioning speed)
and #5 (maximum acceleration) — entirely separate from `reference_search_speed`/`reference_switch_speed`, which only
apply to `PUT /home`. `max_positioning_speed`/`max_acceleration` default to `51200`/`500000` precisely because,
before that default existed, a board that had never had #4/#5 set (e.g. right after a power cycle, since axis
parameters are volatile SRAM) would report `MVP` success while producing no motion at all, with homing still
working normally. If `PUT /position` still doesn't move your motor, tune these two values up or down for your
rail/motor rather than assuming they're universally safe.

## API

The `fraction-collector` component provides:

* `PUT /position?position=vial_1`
* `GET /position`
* `GET /available_positions`
* `PUT /home`
* `PUT /stop`
* `GET /limits`
* `GET /target-reached`
